## T19 联调前需要解决的问题

以下为汇总 ZIP（`snapshot/`）的静态代码检查结果，尚未通过针对这些问题的运行测试：

1. **避免恢复旧代码。** 本快照的前端不含 T10 已修复的请求超时、写成功后直接显示返回结果、退出期间草稿保护及旧 CSRF 恢复；也不含 T11–T13 的搜索、匹配和通知模块。直接覆盖会丢失已有工作。
2. **认领与公告锁定未衔接。** `ClaimService.submit` 未更新公告状态、`claim_guards` 或 `active_reservations`，也未验证关联失物必须仍为 Open。根工程的公告编辑与关闭保护依赖这些共享状态，需要统一事务规则。
3. **批准唯一性不足。** `ClaimService.decide` 接受 Pending 和 Held，却不检查是否已有 Approved，也没有为关联失物取得唯一预留；仅锁拾获公告行不足以证明“一件物品和关联失物最多一次有效批准”。读取认领发生在加锁前，需在锁内重新检查状态。
4. **争议与重复确认保护未完成。** `confirmReturn` 的服务器端路径没有检查 `disputed`；界面隐藏按钮不能替代服务端约束。已确认的一方重试会报错，尚无业务幂等记录。取消批准也尚未清除确认并重算公告及其他认领状态。
5. **指定审核权限尚未实现。** 私密读取和会话仅允许双方参与者，指定审核员没有对应授权；`ModerationService` 按全局 MODERATOR 角色处理全部举报，未验证案件指派。`reviewer_id` 在批准时被写为公告作者，不能视为指定审核员机制。
6. **状态变更与审计事件需接通。** 归还、取消和隐藏直接更新状态，尚未接入公告历史、材料版本、匹配/通知失效及统一审计。隐藏把状态改为 HIDDEN，而现有查询使用独立 `hidden` 字段；必须明确与根工程的状态模型保持一致。

单独上传的 T16/T17 `ClaimService` 与 T18 控制器、审核服务属于另一套实现，与汇总 ZIP 的接口、表结构及逻辑不同。该 `ClaimService` 增加了争议服务端检查、拾获物批准检查及部分共享状态写入，但仍允许所有 MODERATOR 读取私密案件，未限制终态会话写入，关联失物没有唯一预留，`claim_guards` 的变更也未按单个认领隔离。该 `ModerationService.insertReport` 的 INSERT 列数、值表达式数和参数数不一致，需要修正并验证。不能把两套文件混合视为已联调版本；归档的并发测试源码亦不等于本次已执行通过。

`ConcurrentApproveTest` 针对同一个认领发起 20 次并发批准；它没有覆盖需求中的 20 轮全新案件、每轮两个竞争认领，也没有覆盖不同拾获公告对同一关联失物的竞争预留。

后续应在独立的 T19 分支逐项联调，并运行竞争批准、双方确认、争议、权限隔离、关闭锁定、匹配/通知失效和旧功能回归测试。本次归档不修改飞书已有的复核结论，也不将这些未验证行为记为通过。
